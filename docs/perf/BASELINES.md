# Perf baselines (k6 harness)

Sprint 3, D18. This document defines the **structure** for perf baselines.
Actual numbers are owner-generated by running `make perf-baseline` against a
live local stack; the harness exists, the numbers do not yet.

## Why baselines

Without baselines, "is this regression?" becomes opinion. With them, the answer
is `current.json` vs `baseline.json`, diffed by tooling, asserted in CI.

## Existing harness

- `tests/load/k6_baseline.js` — three scenarios: steady / spike / soak.
- `make perf-baseline` — writes `tests/load/results/baseline_<ts>.json`.
- k6 thresholds inside the script enforce hard gates per run.

## Budgets per request kind

The k6 script tags every request as either `read` or `write` and applies these
thresholds (already wired in `k6_baseline.js`):

| Tag | p95 budget | p99 budget | Rationale |
|-----|------------|------------|-----------|
| `read` | 500 ms | 1000 ms | dashboard + lists; user-perceived |
| `write` | 800 ms | 1500 ms | food log POST + recalibration triggers |
| (global) error rate | < 0.5% | n/a | abnormal upstream / DB error budget |

These are **starter budgets**, set by the architecture review. They MUST be
re-calibrated against the first real baseline run on the production-sized VPS.

## Per-endpoint budgets (to be filled by owner)

The endpoints below are the hot-path set the steady scenario exercises. Each
row needs `p95_ms` + `p99_ms` measured against the local stack on cold cache
and warm cache. Until then, the budget column is the architecture target.

| Endpoint | Method | Target p95 | Target p99 | Measured p95 | Measured p99 | Notes |
|----------|--------|------------|------------|--------------|--------------|-------|
| `/logs/food/totals/today` | GET | 200 ms | 400 ms | TBD | TBD | hot Redis cache expected |
| `/logs/food?limit=20` | GET | 250 ms | 500 ms | TBD | TBD | pgsql LIMIT 20 with covering idx |
| `/logs/water/today` | GET | 150 ms | 300 ms | TBD | TBD | sum aggregate; should be sub-100 |
| `/gamification/streak` | GET | 100 ms | 200 ms | TBD | TBD | single row lookup |
| `/gamification/achievements` | GET | 200 ms | 400 ms | TBD | TBD | list of rows |
| `/me/subscription` | GET | 100 ms | 200 ms | TBD | TBD | single row |
| `/progress` | GET | 400 ms | 800 ms | TBD | TBD | heavier aggregation |
| `/fasting/active` | GET | 100 ms | 200 ms | TBD | TBD | single row |
| `/logs/water` | POST | 250 ms | 500 ms | TBD | TBD | single insert + invalidation |
| `/plans/current` | GET | 500 ms | 900 ms | TBD | TBD | join-heavy |

Excluded from p95 budget enforcement (separate scenarios):

- `POST /vision/photos` — large payload + queue handoff. Budget tracked
  separately in vision context.
- `GET /coach/stream` — SSE stream, not request/response.
- `POST /plans/generate` — multi-second LLM call, async by design.

## How to capture a baseline

```bash
# 1. Bring up the local stack
make docker.up

# 2. Seed test users + tokens (owner-side script; pending)
# .venv/bin/python -m scripts.seed_load_users

# 3. Run baseline
BASE_URL=http://localhost:8000 TOKEN=<bearer> make perf-baseline

# 4. The summary lands at
ls tests/load/results/baseline_*.json
```

## How to compare against the baseline

(Pending tooling. Proposed approach:)

```bash
.venv/bin/python -m scripts.perf_diff \
    --baseline tests/load/results/baseline_<accepted>.json \
    --current tests/load/results/baseline_<latest>.json \
    --tolerance 0.10
```

Fails CI if any endpoint's p95 regresses by more than 10% vs accepted baseline.

## What this document is NOT

- It is not a marketing perf sheet. Numbers here are local-stack-only.
- It does not include numbers — running k6 is owner-driven (cost + capacity
  considerations), this PR provides only the harness and the placeholders.
